## The system

Axiōma is an AI IT-support platform. An employee opens a ticket in the portal. **Axel**, the agent, reads it, gathers evidence with read-only tools, and either resolves it — against Kubernetes, or against the employee's laptop via **axel-cli** — or escalates to a human working the dashboard. Every attempt produces an ordered transcript.

Five independent projects under `axioma/`, not a monorepo, no shared package manager:

| Project | Language | Job |
|---|---|---|
| `api` | TypeScript | oRPC for the frontends, gRPC gateways for both agents. **The only component that writes.** |
| `portal` | TypeScript SPA :3001 | Employee-facing |
| `dashboard` | TypeScript SPA :3002 | IT-staff-facing |
| `agent` | Python | Axel — reasoning loop, tool registry, model client |
| `cli` | Go | axel-cli — one static binary on a laptop |

(There is also `web/`, a marketing site. Out of scope unless it is your component.)

## Rules no plan may break

1. **Axel has no database, cluster or device credentials.** Every side effect is a `ToolRequest` to the API, which executes it and returns the result. Axel decides; the API acts and persists.
2. **The contract file imports only `@orpc/contract` and `zod`.** It is mirrored verbatim into both frontends, which have no database, auth module or Hono context. Handlers live in `api/src/server/`.
3. **Never edit `src/sdk/contracts/` in a frontend.** It is generated by `cd api && pnpm contracts:publish` and overwritten.
4. **`api/proto/axioma.proto` is the source of truth**, mirrored into `agent/` and `cli/`. Both agents are gRPC *clients* dialling into the API; neither can be dialled directly.
5. **Frontends use shadcn/ui style `base-lyra` on `@base-ui/react`.** No Radix. Headless libraries such as `@tanstack/react-table` and `recharts` are fine.
6. **Forms use `@tanstack/react-form`**, not react-hook-form.
7. **Every write tool names the read tool that verifies it.** A write returning success means the call was accepted, not that the problem is fixed.
8. **No authorization or permission checks.** Out of scope by decision. Better Auth provides identity only.

## ITSM alignment — use ITIL 4, do not invent

Where the domain is underspecified, follow ITIL 4 rather than inventing structure. Do not overthink it: adopt the standard shape and move on.

**Incident vs Service Request — get this distinction right, it drives everything else.**
An *incident* is an unplanned interruption to a service, or a reduction in its quality. The objective is to restore normal service as fast as possible. A *service request* is a pre-defined, low-risk ask — a password reset, access to software, a new device — that does not disrupt an existing service. Incidents are prioritised by impact and urgency; requests follow a fulfilment workflow and are generally handled in order received.

Axiōma's current schema models only one thing. Decide explicitly whether to add a record type discriminator, and say why.

**Priority is derived, never entered directly.** Priority = Impact × Urgency, resolved through a matrix to P1–P4. Impact is the breadth of business effect; urgency is how fast resolution is needed. Store impact and urgency, compute priority.

**Categorisation is hierarchical** — a broad category narrowing to subcategory. It exists to route and to report, so keep the tree shallow and real.

**Lifecycle**: detect/log → categorise → prioritise → investigate and diagnose → resolve and recover → close. Our states (`open`, `routing`, `resolving`, `resolved`, `escalated`, `closed`) map onto this but are not ITIL's names. Standard states are New, In Progress, On Hold/Pending, Resolved, Closed, plus Cancelled. **Resolved and Closed are distinct** — resolution is technical, closure is confirmed. That distinction matters here because Axel resolves autonomously and a human or the reporter confirms.

**Relevant ITIL 4 practices** and where they land: Incident Management (the ticket spine), Service Request Management (the second record type), Service Desk (portal and dashboard), Monitoring and Event Management (out of scope — we are reactive by decision), Problem Management (out of scope), Service Configuration Management (our CMDB), Change Enablement (out of scope, but note that Axel patching a deployment is a change in ITIL terms and say so honestly).

**Missing fields.** The schema today has no `impact`, `urgency`, `priority`, or `category`. Aligning means adding them. Say exactly which columns, with which enums, and note that schema changes ripple into the contract and both frontends.

**Do not gold-plate.** No SLA engine, no CAB workflow, no full CMDB relationship model. Adopt the standard field set and the standard state machine; stop there.

## Frontend work — do not build components from scratch

For `portal` and `dashboard`, source components rather than authoring them:

- `https://ui.shadcn.com/docs/components` — the component catalogue. Prefer these, adapted to Base UI where the shadcn version ships Radix.
- `https://21st.dev/community/templates` — layouts, page compositions and blocks worth adapting.

For each screen, name the component or block you intend to start from. A plan that says "build a data table" without naming a source is not finished.

Reuse what already exists in `src/components/ui/` before adding anything. Where a sourced component is Radix-based, the plan must say how it is adapted to Base UI — that is real work and must be estimated, not waved through.

## Component focus

- **`api`** — the ITIL schema decisions, contract procedures, the two gRPC gateways, device presence and command dispatch with sequence and replay, the Kubernetes connector, and executing tool requests on Axel's behalf. **Plan this component first; the others depend on its decisions.**
- **`agent`** — the run loop against a real model, prompt construction, tool selection and validation, streaming steps as they happen, run limits and the escalate-rather-than-act judgement.
- **`cli`** — the daemon connection, heartbeat, reconnect with backoff and jitter, sequence replay, the typed action set, the operator commands on Bubble Tea, and Windows install and packaging.
- **`dashboard`** — queue, ticket detail with full transcript, devices, overview. Density suited to someone working it all day.
- **`portal`** — open a ticket, follow it, see the outcome. Plain language only; never raw tool output or model reasoning.

## The plan must contain

1. **Current state** — what exists, what is stubbed, what is missing, and today's gate results.
2. **Gaps** — the difference between that and finished, as a list.
3. **Milestones** — dependency-ordered. Each states what gets built, which files change, and the observable condition that proves it done. No milestone ends in "it compiles."
4. **Cross-component impact** — anything this plan forces on another component, especially contract, proto or schema changes.
5. **Decisions taken** — every place you chose between reasonable options, with the reason. Especially ITIL modelling choices.
6. **Risks** — at most six, each with a concrete mitigation.
7. **Definition of done** — checkable conditions, not adjectives.

## Constraints on the plan itself

- Concrete over abstract. Name files, procedures, columns, components.
- Estimate honestly. If something is a day, say a day.
- If the existing design is wrong, say so and propose the change — do not silently plan around it.
- Do not plan work in other components' directories. Note the dependency and let their plan own it.
- Do not pad. No restating this brief back.
