# CUA computer-server spike

Checked against the current `trycua/cua` computer-server documentation.

- Install: `pip install cua-computer-server[driver]`
- Launch: `python -m computer_server --backend cua-driver --capture-scope desktop`
- Bind: `127.0.0.1:8000` by default; no authentication is documented for loopback.
- Surfaces: REST/WebSocket (`/status`, `/cmd`, `/ws`) and optional MCP (`/mcp`).
- Authentication: none in default loopback mode (`CONTAINER_NAME` unset); keep it bound to loopback.
- Version probe: `POST /cmd` with `{"command":"version","params":{}}`; `/status` does not include the package version.
- The server exposes low-level screenshot, pointer, keyboard, window, accessibility, shell, and file primitives.

## Gate result

There is no objective-submission endpoint and no server-side reasoning loop. Therefore the proposed CLI contract “submit an objective and receive a step transcript” does not exist. Implementing reasoning in `axel-cli` would violate the component boundary (the CLI holds no reasoning), while forwarding a free-form objective as a shell or input command would violate the typed-action trust boundary.

The base CLI implements short-TTL availability/version detection and preserves the required refusal when an objective arrives. Positive computer-use dispatch must be respecified as typed GUI steps generated by Axel (with corresponding proto/API schema), or delegated to a separate reasoning service, before it can be implemented safely.
